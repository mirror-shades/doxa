    Debugging Doxa programs

    Doxa writes standard debug information and leaves debugging to the tools you already have. It ships no debugger of its own.

    Building with debug info

    Every run and compile carries debug information unless you pass --strip:

    doxa compile main.doxa -o bin/main          # with debug info
doxa compile --strip main.doxa -o bin/main  # without

    The debug information is a line table for every .doxa file the program was built from, with its functions, locals and types. Where it lives depends on the platform:

    • Windows: a .pdb beside the binary (bin/main.pdb).
    • Linux: a .debug file beside the binary (bin/main.debug), which the binary names in a .gnu_debuglink section. gdb, lldb and perf find it there; ship the binary alone, and keep the .debug file to debug crashes from it. Both carry the same build ID, a hash of the program, which debuginfod servers and .build-id/ debug directories index by.
    • macOS: in the object files in the compiler's cache, which the binary points to, and, for doxa compile when dsymutil is installed (it comes with Xcode's command-line tools), in a .dSYM beside the binary (bin/main.dSYM), which lldb, Instruments and crash reporters find by the binary's UUID on any machine. A fault's backtrace reads only the cache's objects, so a binary moved to another machine, or run after its cache is cleared, prints its fault line without one. (TODO: read the .dSYM too, once Zig's reader can.)

    It costs the program nothing: the machine code is the same with and without it, but for the start-up that turns backtraces on. Nor does it cost measurable compile time. --strip leaves no debug information at all, the runtime's and libc's included, and no faults' backtraces: on Linux that is most of a binary's size.

    What a debugger sees:

    • Functions under the names the program gives them: scale, or Point.norm for a method. DWARF also records each one's mangled link name (__doxa_m1_…) as its linkage name.
    • Lines and columns. A step moves one statement at a time and stops at the statement's start, such as the if of if x > k. A crash, a breakpoint or a profiler sample inside a statement is attributed to the expression that was running.
    • Locals, parameters and globals under the names the program spells: a var, a parameter, this, a ^ parameter, a binding an as or a match arm declares, and a module-level global. A local lent as ^, and a string variable, are read from their storage; every other is named where it is defined, so an assignment inside a branch shows the value it holds there.
    • Types. int, float and byte are their scalar types; tetra and every enum are enumerations of their values; a string value is its pointer and length, and a string variable's storage adds cap, the bytes its buffer can hold before it moves (strings); a struct is its fields, each at the offset the runtime lays it at; a union or group is its box. A fixed array expands element by element. A dynamic array points at its header: len is its length and data points at its elements, so view data as an array of len to browse them. A function value is a pointer to its signature, and each function's own signature is described.
    • Optimized builds (--opt=1..3) keep what survives optimization. That is the usual optimized-debugging experience: a statement the optimizer merged away has no stop of its own, and a value it folded away has no name.

    Backtraces on fault

    A program follows a runtime fault's line with the Doxa frames that led to it, innermost first:

    Index out of bounds at b.doxa:2:12: index 7, length 3
  in get at b.doxa:2:12
  in outer at b.doxa:6:5
  in main at b.doxa:11:5

    Each frame is named as the program spells it, at the line and column of its call. The runtime's own frames are left out, and so is the call into the entry function. A fault while a global's initializer runs shows that initializer as <globals>. Optimized builds keep the frames that survive inlining. On Windows an inlined function still shows a frame of its own, though CodeView often records no column there (b.doxa:2:0); on Linux and macOS its code is shown under the function it was inlined into, at its own line. The trace goes to stderr and doesn't change the exit status. Under --strip the fault prints its line alone.

    A trace shows at most 64 frames. A run of one frame, as deep recursion makes, prints once and then its count, and a trace cut short says so:

    Stack overflow
  in walk at t.doxa:1:61
  in walk at t.doxa:1:72
  ... the frame above 62 more times
  ... more frames not shown

    When no frame can be shown, a line says why instead, such as (no backtrace: the stack could not be unwound to the faulting frame).

    A trap that is not a fault is a crash: a bad access or an illegal instruction in an inline zig block, say. It prints its line and the Doxa frames that led to it, and the program ends with the platform's crash status (an access violation on Windows, a signal elsewhere), as a native program would:

    Invalid memory access at address 0x10
  in main at crash.doxa:9:5

    doxa run then names how the program ended, as in doxa: the program crashed: access violation (0xC0000005) or doxa: the program was stopped by signal SEGV, and exits 1. A program that exits on its own passes its status through.

    Finding the source

    Debug information names each file by its path inside the project (main.doxa, lib/util.doxa), and a standard-library file by its place in std (std//io/io.doxa). It never records a path on the machine that built it, so a binary built in one checkout debugs the same in another. Point your debugger at the project directory once: directory <project> in gdb, settings set target.source-map in lldb, or the source-file search path in Visual Studio and WinDbg. Windows tools show such a file under a drive root, as C:\main.doxa.

    Profiling

    The same line table lets a sampling profiler (perf, ETW/WPA, VTune, Superluminal, Instruments) attribute samples to .doxa lines. Profile an optimized build (--opt=2): it measures the program you ship.

    A sampler answers how long. To learn how often, instrument the build:

    doxa run fib.doxa --instrument=calls
doxa report fib

    ==========================================
Calls
==========================================
Built at -O0.

  177   fib fib.doxa:1:10
  1 main    fib.doxa:6:23

    Each function counts its own entries, hottest first. --json prints the same data for tooling. An instrumented program writes its counts when it ends: returning from the entry, at @exit, or at a fault. They go to <binary>.profdata, beside the <binary>.profmap the compiler wrote. For doxa run that is the cache, so doxa report <stem> finds both there. For doxa compile -o out/fib, it is out/, read with doxa report out/fib; a filename with an extension, such as doxa report fib.exe, is a path beside the invocation directory, just as ./fib is. A report refuses counts from another build of the program. At --opt=1 and up, an inlined function runs no entry of its own, so its calls count toward its caller. An instrumented binary is a diagnostic build: never time it.

    --instrument=lines counts each statement every time it runs, listed by its start (file:line:column) and its function, hottest first. Members combine: --instrument=calls,lines reports both tables. A loop's header counts once, as the loop statement; its condition and step run with the loop and have no row of their own.

    Static findings

    --emit-complexity asks the compiler what each loop repeats, without running anything:

    doxa run loops.doxa --emit-complexity
doxa report loops

    The report lists each function's deepest loop nest, every allocation or heap store made inside a loop with the arena it lands in, calls inside loops to functions that allocate or loop, in their own body or through a function they call (calls load (allocates through parse)), and copies the compiler left to a runtime check inside a loop. An allocation marked ! lands where no iteration of its loop reclaims it, such as an element pushed into an array declared outside the loop. That memory grows with the loop's iterations and is held until its arena closes. The operations are named as --emit-hir names them (array_push, str_concat). The findings are written beside the binary as <binary>.complexity and change nothing in the program. When the same build is also instrumented, one doxa report shows the counts and the findings together, and --json prints both. With --instrument=lines, each section of findings is ordered by how often its statement ran, highest first, and each row says how often ((ran 50 times)), so what cost the run most leads.
